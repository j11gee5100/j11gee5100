## 2. 背景

公司已有 AI 模型平台、禅道和测试/交付流程，但 AI 模型部署到推理设备时，推理环境安装方式高度不统一：

- 不同硬件架构：x86_64、aarch64、arm64、国产 CPU 架构等。
- 不同操作系统：Ubuntu、CentOS、Kylin、UOS、Windows、定制系统等。
- 不同系统版本：例如 Ubuntu 20.04/22.04、Kylin V10 等。
- 不同推理卡厂商和型号：NVIDIA、昇腾、AMD、寒武纪等。
- 不同驱动、固件、CUDA/CANN/ROCm、Python、推理框架和推理服务版本。
- 安装包来源、安装顺序、依赖关系、冲突关系经常依赖人工经验。
- 最终交付给测试或总装时，缺少标准化大包、总安装脚本、清单和可追溯构建记录。

当前最急迫需求不是完整测试管理，也不是设备实施闭环，而是：

> 建立一个环境安装包资产库，根据目标硬件/系统/架构/推理卡条件筛选可用包，再按安装顺序组合生成独立环境包和总安装脚本。

## 3. 产品定位

平台定位：

> AI 推理环境安装包编排与出包平台。

它管理的是“环境工程资产”，而不是单纯的设备台账。

核心价值：

- 把零散安装包标准化。
- 把适配条件显性化。
- 把安装顺序和依赖关系配置化。
- 把人工拼包过程平台化。
- 把最终交付物标准化为“大包 + 总脚本 + manifest + 构建记录”。

## 4. 一期范围

### 4.1 一期必须做

1. 环境安装包管理。
2. 安装包版本管理。
3. 安装包适配条件管理。
4. 根据目标环境筛选可用安装包。
5. 环境组合方案管理。
6. 安装顺序编排。
7. 生成总安装脚本。
8. 生成环境包 manifest。
9. 生成大环境包构建记录。
10. 保留后续对接模型平台、测试平台、总装交付的字段和接口。

### 4.2 一期暂不做

- 不做完整设备实施记录闭环。
- 不做完整测试管理。
- 不做自动化远程安装。
- 不做 GPU 资源调度。
- 不做 Kubernetes/KServe 部署平台。
- 不做复杂审批流。
- 不做完整交接单生命周期。

## 5. 用户角色

| 角色 | 主要诉求 |
|---|---|
| 环境包维护人员 | 维护驱动、运行时、框架、推理服务等安装包版本和适配规则。 |
| 环境包编排人员 | 按目标硬件/系统条件筛选安装包，选择版本和安装顺序，生成大环境包。 |
| 模型工程师 | 知道某个模型应该选择哪套环境组合或环境包。 |
| 测试工程师 | 获取标准化环境包并执行测试。 |
| 总装/交付人员 | 获取经过测试的环境包、总脚本和 manifest。 |
| 平台管理员 | 管理字典、包仓库、权限、构建记录和审计。 |

## 6. 核心业务对象

### 6.1 环境安装包 Package

表示一个可复用的安装资产，例如：

- NVIDIA Driver
- CUDA
- cuDNN
- TensorRT
- Python Runtime
- PyTorch
- ONNX Runtime
- OpenVINO
- Ascend CANN
- Triton Server
- vLLM
- 自研推理服务
- 业务依赖包

安装包需要记录：

- 包名称。
- 包类型。
- 版本。
- 文件 URI。
- 文件校验值。
- 安装脚本片段。
- 卸载脚本片段，可选。
- 安装脚本与安装后成功检查脚本必填；安装前检查脚本不作为脚本包必需项。
- 安装后验证脚本，可选。
- 是否需要 root。
- 是否需要重启。
- 是否支持离线安装。
- 维护状态。

### 6.2 适配条件 Compatibility Rule

用于声明某个安装包版本适合哪些目标环境。

核心维度：

- 硬件厂商。
- CPU 架构。
- 操作系统。
- 操作系统版本。
- 推理卡厂商。
- 推理卡型号。
- 驱动版本范围。
- CUDA/CANN/ROCm 版本范围。
- Python 版本范围。
- 内核版本范围，可选。

### 6.3 包依赖 Dependency

用于声明安装包之间的依赖和冲突。

关系类型：

- requires：必须先安装。
- conflicts：不能共存。
- recommends：推荐安装。
- replaces：替代旧包。

### 6.4 环境组合方案 Environment Recipe

表示一次环境编排方案：

- 目标硬件/系统条件。
- 选中的安装包版本列表。
- 安装顺序。
- 总脚本生成策略。
- 输出包名称和版本。
- 说明和适用模型，可选。

### 6.5 环境构建产物 Environment Bundle

表示最终输出的大包：

- bundle 编号。
- bundle 名称。
- bundle 版本。
- 关联 recipe。
- manifest。
- 总安装脚本。
- 包文件 URI。
- 构建状态。
- 构建人和构建时间。
- 测试状态，可选。
- 交付状态，可选。

## 7. 核心流程

### 7.1 安装包入库流程

```text
上传/登记安装包
  -> 填写包类型和版本
  -> 配置适配条件
  -> 配置安装脚本片段
  -> 配置依赖/冲突关系
  -> 启用包版本
```

### 7.2 环境组合流程

```text
选择目标硬件/系统/架构/推理卡
  -> 平台筛选可用安装包版本
  -> 用户选择需要的包
  -> 用户调整安装顺序
  -> 平台校验依赖和冲突
  -> 保存环境组合方案
```

### 7.3 出包流程

```text
选择环境组合方案
  -> 生成 manifest.json
  -> 生成总 install.sh
  -> 汇总子安装包和子脚本
  -> 打包成独立大包
  -> 生成构建记录
  -> 输出下载/对象存储 URI
```

### 7.4 后续测试/交付流程

```text
环境大包生成
  -> 交给测试平台或测试工程师
  -> 测试结果回写，可选
  -> 交给总装/交付，可选
```

## 8. 功能需求

### 8.1 安装包管理

- 支持新增、编辑、查询、停用安装包。
- 支持包类型分类。
- 支持版本管理。
- 支持文件 URI 和校验值。
- 支持脚本片段配置。
- 支持 root、重启、离线安装等标记。

### 8.2 适配条件管理

- 支持为安装包版本配置适配条件。
- 支持按目标环境筛选可用包。
- 支持宽松匹配和精确匹配两种模式。
- 一期可使用字段匹配，后续扩展版本范围和表达式规则。

### 8.3 依赖和冲突管理

- 支持配置包之间的依赖顺序。
- 支持配置冲突关系。
- 保存组合方案前必须校验依赖和冲突。
- 一期可先做显式依赖校验，不做复杂 SAT 求解。

### 8.4 环境组合方案管理

- 支持按目标环境创建组合方案。
- 支持从筛选结果中选择包版本。
- 支持调整安装顺序。
- 支持保存 recipe。
- 支持复制 recipe 形成新版本。

### 8.5 出包管理

- 支持基于 recipe 生成 bundle。
- 支持生成 manifest。
- 支持生成总安装脚本。
- 支持记录构建状态和构建产物 URI。
- 支持失败时记录失败原因。

### 8.6 manifest 要求

manifest 至少包含：

- bundle 基础信息。
- 目标环境条件。
- 安装包清单。
- 安装顺序。
- 每个包的版本、校验值、路径。
- 是否需要 root。
- 是否需要重启。
- 生成时间和构建人。

### 8.7 总安装脚本要求

总脚本需要：

- 设置严格执行模式。
- 输出安装阶段日志。
- 按顺序执行子包安装脚本。
- 在每步后执行校验脚本，可选。
- 任一步失败时停止并返回错误。
- 生成本地安装日志。

## 9. 非功能需求

- 可复用：安装包可被多个 recipe 使用。
- 可组合：多个包可按顺序组合成一个环境包。
- 可追溯：bundle 可追溯到 recipe 和每个包版本。
- 可离线：支持内网离线部署场景。
- 可校验：包文件有 checksum，脚本有安装后验证。
- 可扩展：适配维度可以扩展到更多推理卡和国产系统。
- 安全：脚本入库和修改应记录审计，后续可加入审批。

## 10. 一期验收标准

- 可以创建至少 5 类安装包类型。
- 可以为安装包配置硬件/系统/架构/显卡适配条件。
- 可以输入目标环境条件并筛选出可用包。
- 可以选择多个包并调整安装顺序。
- 可以校验基础依赖和冲突。
- 可以保存环境组合方案。
- 可以基于组合方案生成 manifest。
- 可以生成总安装脚本。
- 可以记录 bundle 构建产物和状态。
- 设备实施、测试、总装交接不作为一期验收阻塞项。
