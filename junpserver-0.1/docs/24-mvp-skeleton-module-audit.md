# MVP 架子版模块设计审计

- 日期：2026-06-28
- 当前决策：先做“能跑通菜单、数据、权限、草稿流转”的系统架子；所有会引入规则引擎、远程执行、脚本生成、打包下载、状态机的能力先延后。
- 审计结论：上一版方向正确，但粒度偏细。现在应把“推理环境交付平台”拆成 **资产登记骨架 + 设备适配骨架 + 交付包草稿骨架**，先验证业务对象和页面关系是否成立。

## 0. 架子版定义

架子版只回答 4 个问题：

1. 用户登录后，能否按角色看到正确菜单？
2. 用户能否维护自己的安装项资产？
3. 安装项能否关联设备/适配配置，形成后续筛选基础？
4. 用户能否选择多个安装项保存成一个交付包草稿，并看到 manifest 预览？

架子版不回答这些问题：

- 现场如何自动安装？
- 总控 `install.sh` 如何生成？
- `state.json` 如何断点续装？
- 探测脚本如何远程执行？
- 多厂商设备画像 schema 如何统一？
- 依赖冲突如何自动求解？

## 1. 模块审计结论

| 模块 | 当前处理 | 原因 |
| --- | --- | --- |
| 用户与权限 | 保留，做最小 Admin/User | 没有登录和 owner 隔离，资产管理不成立 |
| 环境包资产 | 保留，作为第一核心模块 | 平台最小单元就是安装项资产 |
| 设备管理 | 保留，但只做台账和适配配置 | 适配条件的来源必须可控，不能在包表单里手填 |
| 探测结果 | 降级为 JSON 导入占位 | 先验证“导入结果 -> 形成/补充设备画像”的入口，不做脚本库 |
| 交付包 | 降级为草稿 + manifest 预览 | 先验证组合关系，不做真实压缩包和总脚本 |
| Admin 管理 | 保留一级菜单 | Admin 管用户和全局资产，不应藏在环境包菜单下 |
| 探测脚本库 | 延后 | 执行环境不可控，容易卡在 schema 和脚本版本管理 |
| 脚本生成器 | 延后 | 需要跨系统路径、日志、错误码、幂等规范 |
| 断点续装状态机 | 延后 | 这是交付包运行时能力，不是当前平台架子必需 |
| 测试平台/模型平台对接 | 延后并预留接口 | 当前核心是环境交付资产，不先做外部系统集成 |

## 2. 本轮一级菜单

本轮只保留 5 个一级菜单：

```text
环境包资产
设备管理
探测结果
交付包
Admin 管理
```

说明：

- `Admin 管理` 只有 Admin 可见。
- 普通用户默认只看自己的资产、设备、探测结果、交付包草稿。
- `探测脚本库` 不单独出现；后续从 `探测结果` 扩展。
- 不新增“实施任务”“在线执行”“测试交接”等菜单。

## 3. 架子版对象边界

### 3.1 用户与权限

最小能力：

- 账号密码登录。
- 角色：Admin / User。
- Admin 可以管理用户、看全局资产。
- User 只维护自己的资产。

暂不做：

- 部门、项目组、租户。
- 细粒度 RBAC。
- 审批流。

### 3.2 环境包资产

目标：管理可复用的最小安装项，例如显卡驱动、Python 环境、FFmpeg、OpenCV、CANN、CUDA、系统依赖等。

架子版字段只保留后续出包必须用到的槽位：

```text
基础信息：名称、类型、版本、文件/存放地址、checksum、状态
适配信息：从设备适配配置中选择，不允许在这里随意手填硬件/系统/架构/显卡型号
脚本槽位：check_script、install_script、verify_script、uninstall_script
编排槽位：install_order、depends_on（文本/JSON 保存，不解析）
归属信息：owner_id、created_by、updated_by
```

暂不做：

- 依赖图解析。
- 冲突求解。
- 脚本模板变量引擎。
- 脚本安全沙箱。

### 3.3 设备管理

目标：提供适配条件来源。

架子版能力：

- 设备台账：设备名称、设备类型、厂商、型号、备注。
- 设备适配配置：系统类型、系统版本、CPU 架构、推理卡厂商、推理卡型号、驱动/运行时版本。
- 安装项资产选择适配条件时，只能从这里选择。

暂不做：

- 平台直连设备。
- 自动执行探测。
- 设备生命周期/维修/库存。

### 3.4 探测结果

目标：预留“现场离线探测结果导入”入口。

架子版能力：

- 上传或粘贴 JSON。
- 关联设备。
- 保存原始 JSON。
- 尽量展示少量核心字段：系统、架构、推理卡、驱动/运行时版本。

暂不做：

- 探测脚本库。
- 多厂商 schema 标准化。
- 自动适配规则生成。
- 画像历史对比。

### 3.5 交付包

目标：验证“多个安装项组合成一个交付包定义”的业务关系。

架子版能力：

- 新建交付包草稿。
- 选择目标设备/适配配置。
- 选择多个安装项。
- 按 `install_order` 或用户选择顺序展示。
- 生成 manifest 预览并保存。

manifest 预览只作为数据确认，不代表已经生成可运行包。

暂不做：

- 真正打包 zip/tar.gz。
- 下载离线交付包。
- 生成完整 `install.sh`。
- `state.json` 断点续装。
- 执行日志回传。

## 4. 最小开发顺序

### 第 0 批：菜单与权限骨架

验收：

- 登录后进入系统。
- Admin/User 菜单不同。
- Admin 管理是一级菜单。
- 普通用户不能进入 Admin 页面。

### 第 1 批：环境包资产 + 设备适配骨架

验收：

- 能新增/编辑设备适配配置。
- 能新增/编辑安装项资产。
- 安装项资产的适配条件来自设备适配配置选择框。
- 能保存脚本槽位、安装顺序、依赖文本。

### 第 2 批：交付包草稿骨架

验收：

- 能选择设备/适配配置。
- 能从可选安装项中选择多个包。
- 能看到 manifest 预览。
- 能保存草稿。

### 第 3 批：探测结果导入骨架

验收：

- 能导入 JSON。
- 能关联设备。
- 能看到原始 JSON 和少量解析字段。

> 如果研发中出现卡点，优先保证第 0/1/2 批；第 3 批可以继续降级为“页面 + 数据表 + 原始 JSON 保存”。

## 5. 明确延后清单

以下能力不是当前架子范围：

- 完整交付包打包下载。
- 总控安装脚本生成。
- 断点续装状态机。
- 现场执行任务管理。
- 探测脚本库和脚本版本管理。
- 多厂商设备画像标准化。
- 依赖冲突自动求解。
- 测试平台前置对接。
- 模型管理平台后置对接。
- 资产共享/转移的复杂流程。

## 6. 当前最小成功标准

本轮架子完成后，只要求可以演示下面链路：

```text
登录
  -> 维护设备适配配置
  -> 维护安装项资产
  -> 安装项选择适配配置
  -> 新建交付包草稿
  -> 选择安装项
  -> 预览 manifest
  -> 保存草稿
```

这条链路跑通，才进入下一轮：真实打包、总脚本、断点续装、探测脚本库。
