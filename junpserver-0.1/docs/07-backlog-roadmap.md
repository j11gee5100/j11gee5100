# OpsPaw 研发 Backlog 与优先级路线图（v0.1）

## 1. 目标

本文件把当前 PRD、接口文档和优化建议，拆成可执行的研发 backlog，并给出建议路线图。

适用场景：

- 立项后排期
- 分工与资源评估
- 版本范围控制
- 识别关键路径与并行工作

## 2. 规划假设

默认按 MVP 试点团队估算：

- 后端：2 人
- 前端：1 人
- QA：1 人
- DevOps/SRE：0.5 人
- 产品/架构：持续参与

默认节奏：

- Sprint：1 周
- MVP：7 周
- 试点上线后再进入增强阶段

## 3. 优先级定义

- `P0`：阻塞项目启动或阻塞任何真实联调
- `P1`：MVP 必需，没有它无法形成可用闭环
- `P2`：增强信任、治理和可解释性，强烈建议在试点前完成
- `P3`：规模化、平台化、长期护城河能力

## 4. 关键路径

真正卡项目进度的主链路如下：

1. JumpServer API 契约确认与 Adapter 基础能力
2. 主数据初始化与同步链路
3. 任务状态机与执行编排
4. 受控执行与审计关联
5. 策略、模板、审批闭环
6. Web 基础界面与 OpenAPI 对接
7. 稳定性、降级、验收演练

以下能力可以并行推进，但不能替代关键路径：

- 看板 UI
- 证据卡展示
- 配置审计页面
- 审计报表
- 场景灰度与模板评分

## 7. 并行推进建议

### 7.1 后端主线

- 优先拿下 B1 -> B2 -> B3 -> B4 -> B5 -> B6
- 不要先做复杂 AI，先把可控执行闭环跑通

### 7.2 前端主线

- 第 1 周开始基于 Mock 接口做 B7-01 ~ B7-04
- 第 4 周接审批、执行、配置页面
- 第 8 周后再做影子模式与证据卡

### 7.3 QA / SRE 主线

- 第 1 周就开始准备 JumpServer 契约测试和初始化压测
- 不要等功能都写完才做故障演练

## 8. 建议资源与角色分工

如果资源紧张，建议最低分工如下：

- 后端 A：JumpServer Adapter、同步、执行链路
- 后端 B：任务状态机、风控审批、OpenAPI
- 前端：Web 全量页面与状态展示
- QA：契约测试、压测、安全测试、故障演练
- DevOps：CI、环境、密钥、监控告警

## 9. 不建议过早做的事情

- 不要先做多 JumpServer source
- 不要先做复杂案例推荐与自动优化
- 不要先做大而全的 CMDB 深度整合
- 不要在 MVP 阶段开放任何自由命令执行

## 10. 我建议的首批 10 个必做项

如果我们只能先做 10 件事，我建议按这个顺序：

1. B1-01 Adapter 认证客户端
2. B1-02 JumpServer 契约测试
3. B2-01 资产初始化同步
4. B2-02 系统用户映射同步
5. B3-01 任务状态机
6. B4-01 命令模板注册表
7. B4-02 JumpServer 执行封装
8. B4-03 执行结果轮询
9. B5-01 风险分级引擎
10. B6-01/B6-02 任务创建与查询 API

## 11. 一句话路线图

先做“可信执行闭环”，再做“可解释和可灰度”，最后做“规模化和平台化”。
